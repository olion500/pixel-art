# Sprite Fusion 픽셀아트 생성기 리버스 엔지니어링 노트

조사일: 2026-10-12 · 대상: https://www.spritefusion.com/pixel-art-generator

근거 수준 표기: **[확인]** = 공식 문서/코드/파일에서 직접 확인, **[추정]** = 관찰을 근거로 한 추론.

## TL;DR

1. **생성 모델은 서버 측 자체(in-house) 모델이며, 16/32/64px "네이티브 해상도"로 직접 생성한다.**
   홈페이지의 "Generation process" 애니메이션은 64×64, 51프레임짜리 디노이징 궤적이고
   처음부터 끝까지 64×64이며 알파 채널(이진 마스크)이 포함되어 있다. → 큰 이미지를 만들어
   축소하는 방식이 아니라, **저해상도 RGBA 픽셀 공간에서 동작하는 diffusion / flow 계열 모델**로 보인다. [추정, 강함]
2. **클라이언트 JS에는 모델 관련 로직이 없다.** 브라우저는 `POST /api/v1/generate`(SSE)만 호출한다. [확인]
3. **"범용 이미지 모델 + 픽셀 필터" 방식의 후처리는 오픈소스 Pixel Snapper로 공개되어 있다**
   (Rust/WASM, MIT). 스스로 "GPT Image 2 / Nano Banana 출력물 수정기"라고 홍보한다. [확인]
   즉 개발자는 범용 모델 출력의 한계를 잘 알고 있고, 메인 생성기는 그 단계를 모델 자체로 대체한 것.
4. 1회 호출(15크레딧)에 **12장**(generate), 9장(style), 8장(8방향), 2장(edit)이 나온다. [확인]
   작은 해상도 모델이라 배치 생성이 싸기 때문으로 보인다. [추정]

## 1. 공개 API 구조 [확인]

Base URL `https://www.spritefusion.com/api/v1`, Bearer 키(`sf_live_...`).

| 엔드포인트 | 설명 |
|---|---|
| `POST /generate` | 모든 작업, `text/event-stream` 응답 |
| `POST /uploads` | 큰 입력 이미지용 서명 업로드 URL (≤20 MiB) |
| `GET /credits`, `GET /assets`, `GET /assets/{id}` | 조회 |

| operation | 필수 | 선택 | 출력 |
|---|---|---|---|
| `generate` | `prompt`, `size` ∈ {16,32,64} | – | 12장 |
| `edit` | `prompt`, `inputs` (1–9, 첫 번째가 주 스프라이트) | – (크기 유지) | 2장 |
| `style-reference` | `prompt`, `inputs` (1–20) | `size` ∈ {16,24,32,48,64,80,96,112,128} | 9장 |
| `direction-set` | `inputs` (정확히 1), **프롬프트 없음** | `size` | 8장 (N…NW) |
| `animate` | `prompt`, `inputs` (1) | `output_frames` (2–16 짝수), `colors` (2–256) | 1 애니메이션 + 스프라이트시트 |

SSE 이벤트: `started`(크레딧 예약) → `progress` → `output`(에셋마다) → `completed`.
웹 에디터도 같은 `/api/v1/generate`를 호출한다 (`animate`는 `colors:24` 하드코딩).

문서 속 단서:
- "grid / contact sheet / atlas / spritesheet를 프롬프트로 요청하지 마라", "개수를 지정하지 마라" —
  여러 변형은 시스템이 자동으로 만든다는 뜻.
- `animate`의 `colors`(2–256) 파라미터 → 애니메이션은 **사후 팔레트 양자화**를 거친다.
- `direction-set`은 프롬프트가 없음 → 내부적으로 고정된 조건(방향 임베딩 등)을 쓰는 전용 모델/모드.
- `edit`/`style-reference`가 최대 9/20장의 레퍼런스를 받는다 → 다중 이미지 컨디셔닝.

## 2. 생성 과정 애니메이션 분석 [확인 → 추정]

파일: `/images/model-generation/poisonous-plant.webp`, `/images/model-generation/magic-fireball.webp`
(`tools/analyze_sprite.py`로 분석)

| 관찰 | 값 |
|---|---|
| 해상도 | 모든 프레임 64×64 (업스케일 없음) |
| 프레임 수 | 51 (≈ 50 sampling step + 최종) |
| 알파 | 매 프레임 0/255 이진, 투명 비율이 ~5번째 스텝 이후 고정 (식물 58%, 불덩이 74%) |
| 프레임 간 변화량 | 초반 90–150 → 10스텝 이후 <10 → 마지막 3스텝 급감 (0.5 → 0) |
| 고유 색상 | 중반 ~3,000 → 마지막 ~900–1,300 (스텝이 진행될수록 감소) |

시각적으로 0스텝은 단색 블롭(전형적인 초기 x₀ 예측), ~8스텝에서 실루엣·구도 확정, 이후에는 디테일과
색만 다듬는다 → **coarse-to-fine 디노이징**의 전형적인 모습.

해석:
- 각 프레임은 매 스텝의 예측 x₀를 디코딩한 것으로 보인다. 64×64 RGBA를 직접 다루는 픽셀 공간 모델이거나,
  아주 작은 latent + 픽셀 디코더 구조. [추정]
- 알파가 처음부터 함께 생성된다 → rembg 같은 사후 배경 제거가 아니라 **RGBA 4채널을 학습**한 모델. [추정]
- 마지막 몇 스텝에서 색상 수가 급감 → 최종 단계에 팔레트 정리(양자화) 또는 저노이즈 정제가 있다. [추정]
- 홍보용 애니메이션이므로 실제 프로덕션 샘플러와 다를 수 있다.

## 3. Pixel Snapper 알고리즘 (오픈소스) [확인]

https://github.com/Hugo-Dz/spritefusion-pixel-snapper (`src/lib.rs`, 약 1,460줄)

1. **색 양자화**: k-means(기본 k=16, seed 42, 최대 15 iter) 또는 사용자 팔레트에 가장 가까운 색으로 매핑.
2. **엣지 프로파일**: 그레이스케일에 `[-1,0,1]` 커널을 적용하고 |gradient|를 열/행별로 합산 → X, Y 1D 프로파일.
3. **스텝 크기 추정**: 프로파일 피크(최대값의 20% 이상, 최소 간격 4px) 사이 간격의 **중앙값** = 픽셀 크기.
   X/Y 비율이 크게 다르면 작은 쪽, 아니면 평균을 쓴다.
4. **Walk cuts**: 0에서 시작해 `step`만큼 전진하고, ±35% 창 안의 최대 엣지 피크에 컷을 스냅한다
   (평균 대비 강도가 낮으면 예상 위치를 그대로 사용). 이후 stabilize/sanitize로 균일화.
5. **리샘플링**: 각 셀 안에서 **최빈 색(다수결)** 을 골라 1픽셀로 만든다 → 디더링이 보존된다.

## 4. 재현 전략 (우리 프로젝트용 제안)

**A. 빠른 경로: 범용 모델 + 후처리 (Pixel Snapper 방식)**
- GPT Image / Nano Banana / Flux + pixel-art LoRA로 생성한다 (단색 배경 지정).
- 배경 제거 → Pixel Snapper (그리드 검출 + k-means + 셀 다수결) → 목표 크기 확인.
- 장점: 즉시 가능. 단점: 그리드 드리프트, mixel, 해상도 제어가 불완전하다.

**B. Sprite Fusion 방식: 네이티브 저해상도 RGBA 생성 모델**
- 데이터: 16/32/64px 실제 픽셀아트 스프라이트(RGBA)와 캡션 쌍. 크기별 버킷.
- 모델: 소형 픽셀 공간 DiT/U-Net diffusion 또는 rectified flow. 입력/출력 4채널(RGBA), 텍스트 조건(CLIP/T5).
  64×64×4는 픽셀 공간에서도 계산량이 작아 한 번에 12장 배치가 저렴하다.
- 샘플링 ~50 step. 마지막에 알파 이진화 + 팔레트 양자화(k-means 또는 고정 팔레트).
- 확장: edit/style은 레퍼런스 이미지 토큰을 컨디셔닝으로 추가하고, 8방향은 방향 클래스 임베딩,
  animate는 프레임 축을 추가한 비디오 diffusion + 공통 팔레트로 양자화한다.

## 6. 재현 실험: 공식 예시(ninja)와 비교

공식 Animator 페이지의 `ninja-base.png`(33×33)와 공식 결과 스프라이트시트(idle 8f, punch 8f, jump 12f)를
기준으로, 생성 모델 없이 **리그 기반 애니메이터**(`tools/rig_animate.py` + `samples/ninja/rig.json`)로 같은 동작을 만들었다.
비교 결과: `out/ninja/compare_{idle,punch,jump}.{png,gif}` (`tools/compare_anim.py`).

관찰한 사실 [확인]: 기준 이미지에는 거의 같은 색이 351개 있지만, 공식 결과는 13~17색이다.
즉 Sprite Fusion도 생성 후 **팔레트 양자화**를 한다(API의 `colors` 파라미터, 에디터 기본값 24).
우리도 k-means++로 16색 팔레트를 만들고, 모든 프레임을 그 팔레트에 맞췄다.

| 동작 | 결과 | 이유 |
|---|---|---|
| idle | 기준과 거의 같은 수준 | 상체 1px 호흡 + 스카프 펄럭임만 필요한 동작이라 부위 이동으로 충분 |
| punch | 비슷한 수준 (팔 길이·몸 기울기는 차이) | 팔을 다시 그리는 방식(어깨→주먹 외곽선 캡슐 + 원본 주먹 픽셀)으로 뻗는 동작 재현 |
| jump | **기준보다 확실히 낮음** | 기준은 무릎을 굽혀 웅크리고, 몸을 펴고, 다리를 접는 등 **자세 자체를 새로 그린다**. 리그의 회전·압축만으로는 관절이 굽는 표현이 안 됨 |

결론: 원래 실루엣 안에서 부위를 움직이는 동작(idle, 짧은 공격)은 리그 방식으로 비슷한 품질을 낼 수 있다.
자세 전체가 바뀌는 동작(jump, run, 회전)은 **새 픽셀을 그려내는 생성 모델**이 있어야 같은 수준이 나온다.
이것이 Sprite Fusion이 자체 모델을 학습한 이유이기도 하다.
현실적인 대안은 이미지 편집 모델로 핵심 자세(keypose) 2~4장만 생성하고, 그 사이 프레임과 팔레트 고정은 이 파이프라인으로 처리하는 하이브리드 방식이다.

## 7. 애니메이션 파이프라인 추가 분석

### 7.1 공식 결과 프레임 정량 분석 [확인]
기준 이미지(`ninja-base.png`)를 결과 팔레트로 양자화한 뒤, 프레임별로 정수 이동(±6px) 중 가장 잘 맞는 위치에서 픽셀 일치율을 쟀다.

| 애니메이션 | 0번 프레임 일치율 | 이후 프레임 | 캐릭터 크기(bbox) | 전체 팔레트 |
|---|---|---|---|---|
| idle | **98.8%** (이동 없음) | 66~93% | 28×33 그대로 | 17색 |
| punch (8f) | 68% | 45~69% | 25~30×33 | 15색 |
| jump (12f) | **22%** | 15~22% | **20~26×24~27 (더 작음)** | 17색 |

해석:
- idle은 0번 프레임이 원본과 거의 같다 → **첫 프레임 = 입력 이미지**로 고정하고 이후 프레임을 생성한다 (PixelLab 문서의 "First frame preserved"와 같은 방식).
- punch와 jump는 0번 프레임부터 원본과 다르고, jump는 캐릭터 크기 자체가 다르다 → 원본을 그대로 애니메이션한 것이 아니라 **Edit로 자세(전투 자세, 웅크림)를 먼저 바꾼 이미지에서 시작**했다.
  공식 문서도 "걷기·달리기·공격·점프는 먼저 edit로 알맞은 시작 자세를 만들고 animate하라", "가만히 서 있는 이미지로는 달리기 루프를 제대로 만들 수 없다"고 안내한다.
- 팔레트는 원본 색과 평균 5~16 정도 떨어진 새 색이다 → 생성된 전체 프레임에서 **하나의 공통 팔레트를 새로 뽑는다** (API `colors` 2~256, 에디터 기본값 24).

### 7.2 다른 서비스와 연구 [확인, 출처는 대화 기록]
- **PixelLab "Animate with text (New)"**: 참조 이미지 1장 + 동작 텍스트 → 4~16프레임(**짝수**), 첫 프레임은 입력 그대로. Sprite Fusion의 `output_frames`(2~16, 짝수)와 같은 형태.
  구버전 Pro는 32/64px 입력에 대해 **16프레임을 4×4 그리드 한 장으로 생성**한다 → 스프라이트시트를 이미지 한 장으로 만드는 방식.
  "Animate with skeleton"은 사용자가 스켈레톤 포즈를 지정하면 모델이 그 포즈대로 그린다 (포즈 조건부 생성).
- **Retro Diffusion**: FLUX 기반 모델을 학습시키고, 군집화로 칸별 색을 정하는 다운스케일 + 색 양자화를 후처리로 한다. 애니메이션은 입력을 첫 프레임으로 유지한다.
- **Sprite Sheet Diffusion** (CMU, arXiv 2412.03685): Animate Anyone 구조(ReferenceNet + Pose Guider + motion module)를 스프라이트에 적용. 참조 이미지 + **포즈 시퀀스**를 입력으로 받는다. 일반 포즈 추정기(OpenPose 등)가 스프라이트에서는 잘 안 맞는다고 보고한다.

### 7.3 결론: 업계의 공통 구조
1. **(필요하면) 자세 편집**: 동작에 맞는 시작 자세를 생성 모델로 만든다.
2. **첫 프레임 고정 + 이후 프레임 생성**: 참조 이미지를 조건으로 넣는다. 그리드 한 장에 여러 프레임을 생성하거나 비디오 모델을 쓰고, 포즈(스켈레톤)를 조건으로 주기도 한다.
3. **후처리**: 픽셀 격자 정렬, 애니메이션 전체 공통 팔레트 양자화(13~24색), 알파 이진화.

우리 리그 방식은 2번을 "생성" 대신 "부위 이동"으로 대체한 것이다. 원래 실루엣 안에서 움직이는 동작은 충분하지만,
jump처럼 1번(자세 편집)이 필요한 동작은 생성 모델이 없으면 품질 한계가 분명하다.

## 8. 개선 v2: 스켈레톤 리그 + 생성 파이프라인

### 8.1 스켈레톤 리그 (`tools/rig_animate.py`, `samples/ninja/rig.json`)
- 다리와 팔을 **관절 체인**(엉덩이→무릎→발목, 어깨→팔꿈치→손)으로 매 프레임 다시 그린다.
  명암과 외곽선을 넣고, 끝에는 원본의 신발·주먹 픽셀을 붙인다(필요하면 RotSprite 방식으로 회전).
- 몸통은 엉덩이를 중심으로 회전한다. 머리는 몸통 회전의 35%만 따라 돌고, 스카프는 목 위치만 따라가고 회전하지 않는다.
- 후처리: 부위 사이에 생긴 틈과 구멍을 채우고, 4px 미만으로 떨어진 픽셀 조각은 지운다.
- jump: 공식 결과처럼 **웅크린 자세에서 시작해서 웅크린 자세로 끝난다**(웅크림 → 도약 → 공중에서 다리 접기 → 착지).
- punch: **뒷손 크로스**. 0번 프레임은 원본 그대로 두고, 몸통 비틀기, 앞발 내딛기, 뒤꿈치 들기, 앞손 당기기를 넣었다.

### 8.2 생성 파이프라인 (`tools/gen_animate.py`)
업계 구조를 그대로 옮겼다: 원본을 정수 배율로 키워 그리드 첫 칸에 넣는다 → Gemini 이미지 모델이 나머지 칸을 채운다
→ 마젠타 배경 제거 → 칸마다 블록 다수결로 원래 해상도로 줄인다(블록 가장자리는 버림) → 원본 팔레트에 맞춤
→ 틈 메우기와 픽셀 조각 제거 → 0번 프레임은 원본으로 고정, 바닥선 정렬.
흐림, 색 노이즈, 정수가 아닌 리사이즈를 넣은 가짜 모델 출력으로 후처리를 검증했다.
**Gemini 이미지 모델은 무료 등급 할당량이 0**이라, 실제 생성은 결제가 켜진 키가 있어야 한다.
